Chapter 3: Cloud Save with Unity Cloud

1. Introduction: From Ephemeral State to Cloud Persistence

In the previous chapter, we explored how Netcode for GameObjects (NGO) synchronizes game state across connected clients in real time. Mechanisms such as NetworkVariable and Remote Procedure Calls (RPCs) operate in volatile memory (RAM) while a multiplayer session is active. However, once the host disconnects or the dedicated server shuts down, all in-memory state is lost.

To retain player progression, inventories, currencies, and shared world states across different sessions and devices, multiplayer games require persistent storage. Historically, studios built custom backend APIs backed by relational databases (such as MySQL or PostgreSQL). In modern game development, however, teams increasingly rely on Backend-as-a-Service (BaaS) platforms like Unity Gaming Services (UGS), which abstract server infrastructure, scalability, and database administration.

Unity Cloud Save is a managed NoSQL cloud storage service designed specifically for games. Under the hood, the SDK communicates asynchronously with Unity’s cloud servers over HTTPS/REST, allowing developers to store structured key-value data and binary files without writing custom web servers.

2. Service Initialization and Player Identity

Cloud Save cannot operate in isolation; it depends on Unity Core Services and Unity Authentication. Every record stored in Player Data is partitioned under a unique PlayerId generated when a user signs in.

Because network requests to cloud servers involve high latency compared to local memory access (typically tens to hundreds of milliseconds), all Cloud Save operations are asynchronous. In C#, they return Task or Task<T> objects and must be awaited using async/await so that Unity’s main rendering thread never freezes while waiting for a server response.


using System.Threading.Tasks;
using Unity.Services.Authentication;
using Unity.Services.Core;
using UnityEngine;

public class CloudInitializer : MonoBehaviour
{
    private async void Start()
    {
        await InitializeServicesAsync();
    }

    private async Task InitializeServicesAsync()
    {
        // 1. Initialize Unity Gaming Services SDK
        await UnityServices.InitializeAsync();

        // 2. Authenticate the player to obtain a unique PlayerId
        if (!AuthenticationService.Instance.IsSignedIn)
        {
            await AuthenticationService.Instance.SignInAnonymouslyAsync();
            Debug.Log($"Signed in with PlayerId: {AuthenticationService.Instance.PlayerId}");
        }
    }
}

Exception Handling and Rate Limits

Unlike local file I/O, cloud operations can fail due to connectivity drops, invalid payloads, or throttling. Production code should wrap SDK calls in try-catch blocks to handle specific exceptions:

  • CloudSaveValidationException: Triggered when data exceeds size quotas, violates schema rules, or fails a write lock check.
  • CloudSaveRateLimitedException: Triggered when a client exceeds Unity’s traffic quotas (by default, up to 600 requests per minute per player). Batching multiple keys into a single SaveAsync or LoadAsync call prevents hitting rate limits.
  • CloudSaveException: Base exception covering general network or server-side errors.

3. Data Modeling and Storage Types

Designing an efficient cloud persistence layer requires choosing the right storage primitive based on data size, structure, and access patterns. Unity Cloud Save divides storage into three distinct categories:

Player Data (Key-Value JSON)

Player Data stores key-value pairs associated with an individual PlayerId. Keys are strings, and values can be primitive types (int, float, bool, string) or complex C# classes marked with [Serializable], which the SDK automatically serializes into JSON.

  • Storage Quotas: Up to 2,000 keys and 5 MiB of total data per player within each Access Class.
  • Use Cases: Player level, experience points, equipped cosmetics, serialized inventories, and gameplay preferences.

Game Data (Custom Items)

Not all persistent data belongs to a single user. Multiplayer games often need to persist shared entities such as clans, guilds, dynamic marketplace catalogs, or global seasonal event parameters. Game Data (accessed via CloudSaveService.Instance.Data.Custom) stores key-value pairs indexed by a developer-defined CustomId rather than a PlayerId.

  • Storage Quotas: Up to 2,000 keys and 5 MiB per Custom Item ID within each Access Class.
  • Use Cases: Guild progression shared among members, global boss health pools, or live-ops balance tables updated without publishing a new game client build.

4. Security and Authority: Access Classes

In Chapter 2, we established a golden rule of multiplayer engineering: never trust the client. If a game client has unrestricted write access to its own currency or competitive rank in the cloud, malicious players can intercept HTTPS traffic or modify client memory to grant themselves unlimited resources.

Unity Cloud Save enforces server authority at the storage layer through Access Classes, which define read and write permissions for clients versus trusted server environments (such as dedicated servers or Unity Cloud Code):

Player Data Access Classes

  • Default: Only the owning player can read and write this data. Other players cannot see it. Ideal for local settings, single-player campaign checkpoints, or non-competitive state.
  • Public: Any authenticated player in the game can read this data (by querying another user's PlayerId), while only the owning player can write to it. Ideal for public profiles, display names, clan badges, or equipped cosmetic skins shown in lobbies.
  • Protected: The owning player can read this data, but only trusted server code (Cloud Code or Admin APIs) can write or delete it. Client write attempts are rejected by the server. Essential for virtual currencies, unlocked items, battle pass tiers, and matchmaking ratings (ELO).

Game Data (Custom Items) Access Classes

  • Default: Any authenticated player can read the data, while only server-side code can write to it. Ideal for global event rules, daily shop rotations, or public guild leaderboards.
  • Private: Completely invisible to game clients; both read and write operations are restricted exclusively to server-side code. Ideal for internal anti-cheat metrics, secret drop-rate tables, or server-only world seeds.

5. Concurrency Control: Write Locks

Modern games frequently support cross-platform play or server-side background rewards. This introduces the classic database problem of race conditions (lost updates).

Consider a player logged into the same account on both PC and mobile simultaneously, or a client saving inventory changes at the exact millisecond a Cloud Code script grants a tournament prize. Without concurrency control, whichever request arrives last blindly overwrites the database, erasing the earlier update.

Optimistic Concurrency with Write Locks

Instead of locking database rows (which degrades scalability over high-latency connections), Unity Cloud Save implements Optimistic Concurrency Control (OCC) via Write Locks:

  1. Every time a key is created, loaded, or updated, the server generates an opaque version token called a writeLock (e.g., "a1b2c3d4") and returns it alongside the data.
  2. When updating a key, the client can wrap the new value inside a SaveItem(value, writeLock) object.
  3. Before committing the write, the server compares the client's writeLock against the current version stored in the cloud.
  4. If they match, the update succeeds and a new writeLock is returned. If another process modified the key in the meantime, the tokens differ and the server rejects the request with a CloudSaveValidationException.
using System.Collections.Generic;
using System.Threading.Tasks;
using Unity.Services.CloudSave;
using Unity.Services.CloudSave.Models;
using UnityEngine;

public class ConcurrencyExample
{
    public async Task SafeUpdateAsync(string key, object newData, string currentWriteLock)
    {
        try
        {
            // Wrap the value in a SaveItem to enforce write lock validation
            var data = new Dictionary<string, SaveItem>
            {
                { key, new SaveItem(newData, currentWriteLock) }
            };

            Dictionary<string, string> result = await CloudSaveService.Instance.Data.Player.SaveAsync(data);
            string updatedWriteLock = result[key];
            Debug.Log($"Saved safely. New writeLock: {updatedWriteLock}");
        }
        catch (CloudSaveValidationException)
        {
            // Conflict detected: reload latest server state, merge changes, and retry
            Debug.LogWarning("Write conflict detected! Data was modified by another session.");
        }
    }
}

Depending on the criticality of the data, developers choose between two strategies:

  • Unconditional (Forced) Writes: Passing raw values instead of SaveItem omits the writeLock check and overwrites the server state unconditionally. Suitable for non-critical settings like audio volume.
  • Validated Writes (Read-Merge-Write): Passing a writeLock (or DeleteOptions { WriteLock = ... } when deleting) guarantees data integrity. On conflict, the client re-downloads the latest version, merges progress, and retries.

6. Indexing and Queries (Cloud Save Queries)

Key-value stores are optimized for $O(1)$ lookups when you already know the exact PlayerId or CustomId. However, multiplayer games often need to search across records—for example, finding guilds with open slots or locating opponents within a specific skill bracket.

Cloud Save Queries provide SQL-like filtering capabilities across Player Data (Public access class) and Game Data (Default access class), subject to strict architectural constraints designed to guarantee predictable cloud performance:

Pre-Declared Indexes

Unlike relational databases that allow unindexed full-table scans, Cloud Save only allows queries on keys explicitly configured as indexes in the Unity Dashboard or via the UGS CLI:

  • Index Quota: A project supports up to 20 indexed keys in total across Player and Game Data, with indexed values capped at 128 bytes.
  • No Retroactive Indexing: Creating an index only tracks writes performed after the index is defined. Existing records saved prior to index creation will not appear in query results until they are updated and re-saved.

Filter Operators and Composite Indexes

Queries combine one or more field filters using standard comparison operators: EQ (equal), NE (not equal), LT (less than), LE (less than or equal), GT (greater than), and GE (greater than or equal). Numeric values are compared mathematically, while strings are compared lexicographically.

When querying multiple conditions simultaneously (e.g., filtering by both Region == "EU" and Rank >= 1500), a composite index must be defined in the exact evaluation order required by the query. Additionally, queries support a sampleSize parameter that returns a randomized subset of matching records—a lightweight technique commonly used for lobby discovery or basic skill-based matchmaking without downloading thousands of records.
